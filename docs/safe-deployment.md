# Безопасный деплой АБС

## Что публикуется

Релиз собирается из конкретного Git-коммита в отдельной временной папке. Незакоммиченные изменения не публикуются: при грязном рабочем дереве команда останавливается **до SSH**. Скрипт не делает коммит автоматически.

Разрешённые пути перечислены в `scripts/deploy-policy.json`: страницы сайта, CSS/JS, изображения/шрифты, robots/sitemap и два PHP-файла формы. При добавлении нового раздела список нужно пересмотреть в коммите. Неожиданный файл сборки блокирует релиз.

`_prototype`, служебные `.gitkeep` и локальный `var/submissions.log` исключены. `.htaccess`, `.user.ini`, `.env`, skills, logs, uploads, Git, рабочие и посторонние папки на сервере не изменяются. Старые серверные файлы автоматически не удаляются. Локальный `dist` целиком больше не загружается.

## Команды

Из корня проекта, после подготовки и фиксации нужного коммита:

```powershell
npm run test:deploy
npm run deploy -- -PlanOnly
npm run deploy
```

`-PlanOnly` выполняет только чтение на сервере: сравнивает SHA-256 и показывает добавления/замены и объём загрузки. Обычный запуск повторяет сравнение и требует подтверждение `DEPLOY`. `-Commit <SHA>` выбирает конкретный коммит. `-Yes` пропускает ручное подтверждение, но не проверки; использовать только после проверки квоты и списка.

Пароль запрашивает OpenSSH; скрипт не хранит его. У разных SSH-соединений пароль может запрашиваться повторно. `StrictHostKeyChecking=yes`: ключ сервера должен быть предварительно проверен и сохранён в `known_hosts`.

## Этапы

1. Изолированная сборка и существующие тесты сайта/формы.
2. Проверка допустимых путей и хешей, чтение состояния хостинга. Символические ссылки не допускаются.
3. После подтверждения — атомарная блокировка `~/abs-engineer.ru/.abs-deploy/lock`. Другой деплой эту блокировку не снимает.
4. Один tar-архив **только изменённых файлов** загружается legacy SCP (`-O`, без `-r` и `-p`) в `.abs-deploy/<ID>/payload.tar`, вне `public_html`. Файлы распаковываются без `extractall`, каждый путь, тип, размер и SHA-256 проверяются.
5. Перед заменой создаётся уникальный `~/abs-engineer.ru/backup-served-ГГГГММДД-ЧЧММСС-ID.tgz` (время UTC), с ACL/xattrs и числовыми владельцами. Это **резервная копия заменяемых файлов**, не полный снимок сайта. Соседний `.tgz.json` и журнал содержат метаданные и перечень добавлений. Архив проверяется распаковкой вне сайта, сверкой хешей и восстановлением метаданных до первой замены.
6. Заменяемые файлы подготавливаются с прежними UID/GID, режимом и ACL. Новые файлы/папки получают ACL назначения; отсутствие default ACL или невозможность сохранить владельца останавливает публикацию. Существующие папки не переименовываются, не заменяются и не подвергаются `chmod/chown/setfacl`.
7. Каждый файл заменяется через `os.replace` в той же файловой системе. Долговечный журнал записывается перед заменой. Проверяются все локальные серверные SHA-256, неизменность прав существующих папок, HTTP главной, CSS/JS, изменённых страниц/изображений и GET обработчика формы. GET должен вернуть 303 на `/request/`; реальная заявка/письмо при проверке не отправляются.
8. При обнаруженной ошибке — восстановление заменённых файлов и их прав. Удаляются только новые файлы/пустые папки этого неудачного запуска, а не старые серверные данные. При конфликте с чужой записью восстановление останавливается и блокировка сохраняется.

Замена атомарна **для каждого файла**, не для сайта целиком: короткое смешанное состояние между заменами возможно. При жёстком завершении процесса/обрыве SSH автоматический откат не гарантирован; журнал и блокировка позволяют продолжить восстановление. Нельзя запускать старый скрипт параллельно с новым.

## Проверить хостинг перед первым релизом

Нужны Python 3.8+, GNU tar с `--acls/--xattrs`, `getfacl/setfacl`, стандартный HTTPS-доступ к домену и право создавать staging/backup рядом с `public_html`. Ничего не устанавливается автоматически.

Пользователь `idealstroy_dev` может иметь ACL на запись, но **не иметь права сохранять владельца `idealstroy` при атомарной замене**. В таком случае релиз остановится без изменения живых файлов. Не исправлять это массовым chmod/chown. После проверки владельца можно запустить с основным аккаунтом:

```powershell
npm run deploy -- -SshUser idealstroy -PlanOnly
```

Дополнительную учётную запись не менять на сервере; параметр только выбирает SSH-логин. `-PlanOnly` проверяет наличие инструментов и возможность чтения, но полное сохранение ACL/владельца проверяется на подготовленных файлах перед заменой.

Свободное место файловой системы не равно доступной квоте аккаунта. Квоту основного аккаунта проверить в Beget вручную. Деплой дополнительно оценивает место для staging/backup, но не заявляет, что квота подтверждена.

## Прерванный запуск

Скрипт выводит ID запуска и сохраняет запрос восстановления локально в `%TEMP%/abs-deploy-request-ID.json`. Он не содержит пароль. На сервере сохраняется `.abs-deploy/ID/journal.json`.

```powershell
npm run deploy -- -StatusRun ID
npm run deploy -- -RecoverRun ID
```

Сначала проверить статус. `complete` означает, что проверенный релиз завершился: восстановление прерванного запуска к нему не применяется. `rolled_back` означает завершённый откат. Для `uploading`, `backed_up`, `publishing`, `rolling_back` или `rollback_failed` — сначала убедиться, что прежний процесс завершён, затем выполнять `-RecoverRun` с тем же SSH-пользователем. Команда откатывает этот запуск, не возобновляет загрузку.

Если локальный запрос потерян или возник конфликт файлов — требуется ручной разбор серверного журнала и архива. Блокировку не удалять вслепую. Архивы и staging автоматически не чистятся, чтобы сохранить возможность расследования; очистка/политика хранения — отдельное согласованное действие.

## Границы проверки

`npm run test:deploy` проверяет локальный manifest/delta и моделирует сбои публикации. ACL и владельцы в этих offline-тестах имитируются: они **не подтверждают возможности Beget**. До первого релиза необходима проверка окружения/учётной записи на хостинге. Внедрение механики само по себе не запускает публикацию.
