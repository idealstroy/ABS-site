# Деплой АБС: адаптация схемы ПТО Онлайн для Beget

## Один механизм, без установок

Запуск: `scripts/deploy-ssh.ps1`. Подготовка на компьютере: Node/Git/tar. На хостинге: обычный `sh`, GNU tar, base64, sha256sum, getfacl и стандартные команды Linux. Команды передаются в Base64 и декодируются до чтения shell, чтобы служебные символы stdin не искажали начало скрипта. Python, rsync, sudo и установка пакетов не нужны.

Единственный список разрешённых путей — `scripts/deploy-policy.json`. Дублирующий `.deploy-config.json`, прежний `deploy-remote.py` и его Python-тесты удалены. Пароли не сохраняются. По умолчанию: `idealstroy_dev@idealstroy.beget.tech`, `/home/i/idealstroy/abs-engineer.ru/public_html`.

## Последовательность

1. Собираем конкретный чистый Git-коммит во временной папке компьютера и запускаем тесты сайта. Русские имена распаковываются в UTF-8. Незакоммиченные изменения блокируют публикацию.
2. Проверяем наличие существующих команд на хостинге и сравниваем SHA-256. Показываем только добавления/изменения и объём загрузки. До подтверждения сервер не изменяется.
3. Передаём один архив **только изменённых файлов** в `~/abs-engineer.ru/.abs-deploy-simple/ID`, вне `public_html`, через legacy SCP (`-O`). Проверяем хеш архива, состав, размеры и хеши файлов. Параллельный запуск блокируется.
4. Сохраняем заменяемые файлы в уникальный `~/abs-engineer.ru/backup-served-ГГГГММДД-ЧЧММСС-ID.tgz` (UTC). Проверяем архив распаковкой и хешами. `.acl` рядом сохраняет ACL/числовых владельцев, `.manifest` — список замен и добавлений. Это бэкап заменяемых файлов, а не всех посторонних данных сервера. До окончания подготовки рабочие файлы не меняются.
5. Обновляем ресурсы, затем HTML, как в ПТО. **Отличие Beget:** существующие файлы обновляются записью содержимого в тот же файл. Его владелец, группа, права и ACL сохраняются. Никаких массовых chmod/chown, переименования `public_html` или замены существующих папок. Новые папки/файлы создаются только при наличии наследуемых ACL.
6. Проверяем хеши обновлённых файлов, HTTP главной, стилей/JS, изменённых страниц и изображений. GET обработчика формы должен вернуть 303 на `/request/`; заявка не отправляется.
7. При сбое обновления shell пытается восстановить файлы. При неудачной HTTP-проверке локальный скрипт вызывает восстановление. После успешных проверок закрываем запуск. Старые файлы и бэкапы автоматически не удаляем.

`skills`, загрузки, логи, настройки `.htaccess/.env/.user.ini` и прочие посторонние файлы не публикуются и не удаляются. Прототипы, `.gitkeep` и локальный журнал формы не входят в архив. При добавлении нового раздела согласованный список путей обновляется в коммите.

## Команды

```powershell
# Только совместимость: чтение на хостинге, без сборки и загрузки
npm run deploy -- -CheckOnly

# Собрать релиз и показать разницу, без загрузки
npm run deploy -- -PlanOnly

# Деплой после фиксации нужных изменений в Git, с подтверждением DEPLOY
npm run deploy

# Локальные тесты механизма, без хостинга
npm run test:deploy
```

Указать коммит: `-Commit <SHA>`. Другой разрешённый аккаунт: `-SshUser idealstroy`. `-Yes` пропускает ручное подтверждение, но не проверки; применять только после проверки списка и квоты.

SSH может запрашивать пароль несколько раз — это разные соединения. Ключ хостинга должен быть предварительно проверен и сохранён в `known_hosts`.

## Если связь оборвалась

Не повторять деплой вслепую. Скрипт выводит ID, сохраняет запрос без пароля в `%TEMP%/abs-simple-request-ID.json`, а на сервере — простую папку запуска со статусом, бэкапом и списком затронутых файлов.

```powershell
npm run deploy -- -StatusRun ID
npm run deploy -- -RecoverRun ID
```

Статусы: `staged` — живые файлы не менялись; `prepared` — архив и бэкап готовы, живые файлы не менялись; `publishing` — обновление началось; `published` — файлы обновлены, подтверждение ещё не закончено; `complete` — проверки завершились; `rolled_back` — восстановлено; `recovery_required` — восстановление не завершилось.

Перед восстановлением убедиться, что прежний процесс остановлен. Использовать тот же SSH-аккаунт. Восстанавливаются только файлы этого запуска; новые файлы и пустые папки именно этого неудачного релиза удаляются. Завершённый релиз через `RecoverRun` не откатывается. Бэкапы и временные папки автоматически не чистятся. При потере локального запроса нужен разбор серверной папки запуска; блокировку не удалять вслепую.

## Важные ограничения

- Обновление содержимого **не атомарное**: во время записи отдельного файла возможна короткая недоступность этого файла. Это компромисс для сохранения существующих владельцев/ACL под дополнительным пользователем Beget. При жёстком обрыве нужен отдельный запуск восстановления.
- Команда восстановления предполагает, что рабочие статические файлы не меняют вручную: команда работает через коммиты и один деплой одновременно. Не использовать старые скрипты параллельно.
- Свободное место диска проверяется, но это не квота аккаунта. Квоту основного аккаунта проверить в панели Beget.
- Локальные shell-тесты выполняются через уже установленный Git Bash на Windows или `/bin/sh` на Linux. Наследуемые ACL в них имитируются; это не подтверждение ACL Beget. Первый реальный шаг — `-CheckOnly`, затем `-PlanOnly`. Никакие дополнительные программы автоматически не устанавливаются.

Старые серверные папки `.abs-deploy` или прежние архивы эта версия не трогает. Их очистка — отдельное согласованное действие.
